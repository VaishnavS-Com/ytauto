# Milestone 4 — Script Generation (Phase 2 begins)

## 1. Goal

One command turns your best-ranked topic into a complete video package —
title, hook, 4-chapter narration script (~600-800 words), and CTA —
generated by your local LLM via a prompt chain, stored in a new `scripts`
table, exported as readable markdown, with the topic advancing
`ranked → scripted`.

## 2. Theory

**Prompt chaining.** One big "write me a full script" prompt gives a small
model too many jobs at once and it loses the plot mid-essay. Decomposition
fixes it: PLAN (structure, cold) → SECTIONS (one per chapter, warm) →
HOOK+CTA (creative, warmest, written last when the full plan is known).
Each output feeds the next prompt. Same principle as Milestone 3
(classification is easier than judgment): a section is easier than an essay.

**Temperature is a dial, not a constant.** 0.4 for the plan (structure
should be stable), 0.7 for narration (natural variety), 0.8 for the hook
(most creative sentence in the video). Cold for facts, warm for craft.

**JSON mode vs plain text.** Steps 1 and 3 need structure → `generate_json`.
Step 2 needs *prose*, and forcing prose through JSON degrades it → the new
`generate_text` in ollama_client. Choose the output mode per job.

**One-to-many, delivered.** In Milestone 1's exercise you chose a separate
`scripts` table with a `topic_id` column because one topic can have many
drafts. That exact design ships here — with a FOREIGN KEY so the database
refuses orphan scripts, and `PRAGMA foreign_keys = ON` because SQLite
(historic quirk) ignores FKs unless asked.

**All-or-nothing generation.** If any step fails, we raise: no partial
script is saved and the topic stays `ranked`, so the next run retries it
free. Compare with ranking, where one failure skipped one topic — here a
half-script is worthless, so the whole unit fails together. Failure policy
should match the unit of value.

**Serialize at the boundary.** Chapters are a Python list everywhere in the
app and a JSON string only inside SQLite. `script_repository` converts at
the edge; no other file ever sees the JSON string.

**The inauthentic-content defense.** YouTube's 2026 policy kills template
channels. The chain generates a *fresh structure per video* (the plan) and
writes prose *against* that plan. Milestone 5 (research injection) will
strengthen this further by feeding real facts into sections.

## 4. Architecture

```
 generate_script.py (CLI)
        │ best_ranked_topic()          [repositories]
        ▼
 generation/script_generator.generate_script()
        │
        ├─ 1. PLAN     gen_json(PLAN_PROMPT, t=0.4)  → parse_plan()
        ├─ 2. SECTIONS gen_text(SECTION_PROMPT, t=0.7) × 4 chapters
        ├─ 3. HOOK+CTA gen_json(HOOK_CTA_PROMPT, t=0.8) → parse_hook_cta()
        │
        ├─ script_repository.save_script()      [one row, chapters as JSON]
        └─ topic_repository.update_status('scripted')
```

## 5. Beginner explanation

You're running a tiny film studio. First the director sketches a storyboard
(the plan — done soberly). Then a writer drafts each scene separately,
storyboard pinned to the wall so scenes don't overlap (sections). Finally
the trailer editor — the most caffeinated person in the building — cuts the
opening hook, which works precisely because the whole film exists first.
Every page goes into the archive cabinet with the film's ID stapled on
(foreign key), and if anyone quits mid-production, the whole draft is
binned rather than shipping half a film (all-or-nothing).

## 8. Common mistakes

1. **One mega-prompt for long content** — decompose; small model, small jobs.
2. **Same temperature everywhere** — structure cold, creativity warm.
3. **Forcing prose through JSON mode** — quality tax for no benefit.
4. **Saving partial results on failure** — half a script pollutes the DB;
   fail the whole unit, keep the topic retryable.
5. **Forgetting `PRAGMA foreign_keys = ON`** — SQLite silently accepts
   orphan rows without it.
6. **Letting JSON strings leak out of the repository** — serialize at the
   storage boundary only.
7. **Hook written first** — write it last, when there's something to hook
   viewers INTO. (Human scriptwriters do the same.)

## 9. Exercises

1. **Generate for real:** `pytest` first (38 passed), then
   `python scripts/generate_script.py`. Takes a few minutes on CPU —
   watch each chain step appear in the log.
2. **Edit like a producer.** Open the exported markdown in `data/scripts/`
   and read it aloud (seriously — it's narration). Find the three worst
   sentences: repetition? generic filler? a wrong fact? Note them —
   they're your prompt-tuning targets.
3. **Tune one prompt.** Based on #2, improve SECTION_PROMPT (e.g. "one
   concrete number or example per section", "vary sentence openings").
   Regenerate for the SAME topic — the two-drafts design exists exactly
   for this A/B comparison. Which draft wins?
4. **Write one test:** `parse_plan` must reject a plan with 7 chapters
   (our range is 3–6). One line of arrange, one assert. → 39 passed.
5. **Thinking:** the body averages ~600-800 words but YouTube retention
   favors tight pacing. Where in the SYSTEM (not the prompt) could you
   enforce "body must be 500-900 words" — and what should happen when a
   draft falls outside it? Connect your answer to the dated_news lesson.
6. **Commit + push**, update PROJECT_STATE.md.
